# M0.11 manual test: live editing and retry-frame

**Exit criterion (ROADMAP M0.11):** change a function while the demo runs, and the change
appears without a restart; cause an error, fix it, choose `retry-frame`, and the game
continues.

**Recorded:** 2026-11-09, macOS (arm64), SBCL 2.6.10, SDL 3.4.20, Cocoa video driver.
The automated test `dev-fix-and-retry-frame` (host/tests/repl.lisp) repeats the error,
fix and retry steps without SDL on every `make test`.

## Steps

Run the bouncing-square demo:

```sh
./skein dev examples/sdl/bounce.skn
```

1. A window opens with an orange square bouncing on a dark background. The terminal
   shows the `examples.sdl.bounce=>` prompt.
2. At the prompt, evaluate `(:x @state)` twice; the values differ, because the square is
   moving.
3. In the editor, change `square-color` to `[40 200 120]` and save.
4. Make an error: change `square-color` to `[40 200 (nth [] 5)]` and save.
5. Fix it: change `square-color` to `[200 60 200]` and save.
6. At the `debug[main thread]` prompt, evaluate `(square-color)`, then type `0`
   (`retry-frame`).
7. Evaluate `(:x @state)` twice again, then type `:quit`.

## Results

| Step | Result |
|---|---|
| 1 | Window opened; orange square bouncing. |
| 2 | `264.28…`, then `144.21…`. |
| 3 | `; reloaded bounce.skn`; the square turned green on the next frame, still moving; `(square-color)` gave `[40 200 120]`. |
| 4 | `; reloaded bounce.skn`, then the next frame failed, and the window froze on the last frame. The terminal showed the error and restarts (transcript below). |
| 5 | `; reloaded bounce.skn` while the program waited in the debugger. |
| 6 | `(square-color)` gave `[200 60 200]`, evaluated in the paused main thread. After `0`: `; resumed`, the square turned purple and kept bouncing from where it stopped (`defonce` kept its position). |
| 7 | `18.32…`, then `138.34…`: moving again. `:quit` stopped the program through its abort restart; the window closed and the exit code was 0. |

Screenshots taken during the run showed the green square after step 3 and the purple one
after step 6. They aren't committed because they show the rest of the desktop.

## Notes

- While the program waits in the debugger, its main thread is stopped, so the window
  doesn't redraw and the OS may show a busy cursor. That is expected in Phase 0. With
  Phase 2 fibers, only the failing fiber stops.
- The demo caps a frame's time step at 0.05 s, so the square doesn't jump after the
  pause.
